# 13 照片解码与导入性能

> 症状（2026-11-16 18:19 用户报）：选壁纸/导入照片慢，"越大分辨率越慢，4K 要等 1 秒多"，
> 而且只是导入设置，不是生成。**实际最慢的是 Vivo Alive 壁纸的素材导入（约 3 秒）。**

## 1. 结论先说

| 问题 | 根因 | 修法 | 效果 |
|---|---|---|---|
| 裁切页/编辑页打开慢 | `ImageDecoder` 即使把目标压到 64px 也要 ~1s（它基本是整幅解码后再缩），比 `BitmapFactory` 慢 3-4 倍 | 新增 `PhotoDecode`（`BitmapFactory` + `inSampleSize`），替换 4 处 `ImageDecoder` | 64MP 照片 1.1–1.5s → **0.25s** |
| Vivo 素材导入慢 | 每张图先解码到 2560，再 **PNG(100) 落盘**（2312×1736 一张 PNG 要 1.7–2.6s） | 不再重新编码：**原封不动复制源文件**（真无损），解码交给引擎按需采样 | 导入 **~3s → 10ms 级**（用户实测"很快，画质没问题"） |
| 编辑页拿到尺寸要整张解码 | `loadImageSize()` 为了拿宽高把 `VivoImages.load()` 整套图（照片+蒙版+画笔）都解码一遍 | 新增 `VivoImages.size()`，只读文件头取宽高 | 省一次 ~80ms 全量解码 |

## 2. 实测数据（同机、同一张照片）

### 2.1 一张 26MB / 9248×6944 的 JPEG

| 路径 | 耗时 |
|---|---|
| `ImageDecoder` target=2048 | 1107–1511 ms |
| `ImageDecoder` target=64 | 971–1158 ms |
| `BitmapFactory` 全尺寸 | 573–964 ms |
| `BitmapFactory` + `inSampleSize=4`（→2312×1736） | 226–241 ms |
| `BitmapFactory` + `inSampleSize=8`（→1156×868） | 235–280 ms（受 I/O 限制，再小也不更快） |
| 文件复制 25MB | 8–11 ms |

注：JPEG 的 1/8 缩放解码仍要扫完整个码流，所以 4 与 8 的差距远小于像素数之比。

### 2.2 编码（2312×1736 位图落盘）

| 格式 | 耗时 | 大小 |
|---|---|---|
| PNG（q100，原逻辑） | **1658–2564 ms** | 6.58 MB |
| JPEG q95 | 64–189 ms | 1.58 MB |

这就是 Vivo 导入"1 秒多"的真正大头——解码只是小头。

### 2.3 Vivo 导入分段（2443×3393 的照片，修复后）

```text
photo decode uri 2443x3393 sample=1 -> 2443x3393 94ms     ← 采样解码
vivo import <w>x<h> jpeg 133ms                            ← 编码落盘（旧版这里是 PNG 的 1.7s+）
vivo import total 243ms for 1 item(s)                     ← 导入完成
```

进一步改成"直接复制"后：

```text
vivo import copy vivo-<uuid>.jpg 11ms
```

## 3. 改动清单

| 文件 | 改动 |
|---|---|
| `PhotoDecode.java`（新增） | 采样解码：`bounds()` 只读头、`decode(File/ContentResolver, maxEdge[, allowBelow])`；`allowBelow` 允许结果落在目标的 0.7–1.4 倍（只用于显示），导出用 `false` 保底不缩水 |
| `MainActivity.importImage` | 导入探针 `ImageDecoder(64)` → `PhotoDecode.decode(file,64)` |
| `PhotoCropActivity` | 预览解码 `ImageDecoder(2048)` → `PhotoDecode.decode(file,1440)`；`export()` 改为"采样解码 + 精确裁剪 + 缩到屏幕尺寸"（不再依赖 `setCrop`） |
| `FrameCropActivity` | 同上，`PhotoDecode.decode(file,2048)` |
| `RenderLoop.loadPhoto` | provider 与文件两条路径都改用 `PhotoDecode.decode(...,2048)`；**provider 只在非预览时使用**（编辑页应读草稿文件，而不是已应用的壁纸） |
| `VivoImages` | `file()` 改用 `PhotoDecode`；新增 `size()` 只读宽高（考虑 slot 旋转后交换宽高） |
| `VivoMediaSelection` | 新增 `importPhoto()`：复制源文件 → 用 `bounds()` 校验可解码 → 校验失败才回退"解码 + JPEG(100)"；两处 `ImageDecoder` 调用一并替换 |
| `VivoEditorActivity.loadImageSize` | 改用 `VivoImages.size()` |

## 4. 为什么"复制原图"比"缩放后重编码"更好

- **无损**：用户明确要求"质量别变"。重编码即便 q100 也是有损的二次压缩。
- **快**：25MB 复制 8–11ms；任何解码/编码都是 100ms 起。
- **代价**：占盘更大（原图多大就多大），引擎加载时要解一次大图（这一点本来也要解，只是源文件更大，多几十到上百毫秒）。
- 想回到"缩一份省盘"的做法：把 `VivoMediaSelection.importPhoto()` 换成 `write(PhotoDecode.decode(resolver,uri,2560))` 即可（质量 100 的 JPEG）。

## 5. 复测方法

1. 工具类已随临时探针一起删除（`PhotoBenchReceiver` 已移除，不应留在正式包里）。要重现基准，按 §2 的写法临时加一个 receiver：生成/指定一张大图，分别计时
   `ImageDecoder(target)` / `BitmapFactory(full)` / `PhotoDecode(maxEdge)` / `compress(PNG,100)` / `compress(JPEG,100)`。
2. 正式包里的常态日志（每次解码一行、每次导入一行，量很小）：
   ```text
   photo decode 9248x6944 sample=8 -> 1156x868 269ms
   photo decode uri 2443x3393 sample=1 -> 2443x3393 94ms
   vivo import copy vivo-<uuid>.jpg 11ms
   vivo import total 243ms for 1 item(s)
   ```
3. 直接量裁切页：`su 0 am start -W -n org.aliveclean/.PhotoCropActivity --es photo <photo-xxx.jpg>`（Activity 未导出，必须 su）。

## 6. 回退

- `PhotoDecode` 是纯新增类，回退只需把调用点换回 `ImageDecoder`（历史见 `git log -S "ImageDecoder" -- app/java/org/aliveclean`）。
- Vivo 导入回退：`importPhoto()` 里删掉"复制"分支，直接 `return write(PhotoDecode.decode(...))`。
