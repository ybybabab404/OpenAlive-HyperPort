## 0. 一句话现状

壁纸服务本身已经稳定（三态场景、AOD 注入、全屏 AOD 判定、系统入口都能跑）。
当前最突出的两个问题是「桌面/锁屏 → 息屏」转场偶发整屏停摆 250ms 级，
以及息屏首帧 NativeScene.render 偶发 150ms 级阻塞；两者都怀疑不在我们的绘制代码里
（前者指向 SurfaceFlinger 合成压力，后者疑似驱动侧等待），但这是运行时观察，尚未独立复测。
除这两条外，§9 还列有 9 条已知问题，不能把本节理解为「只剩这两个问题」。

## 1. 这个项目是什么

把 Flyme 的「Alive 壁纸」那套连贯过渡搬到 HyperOS：
同一张照片（或一套素材）在桌面、锁屏、息屏三态之间连续变化，而不是三段互不相干的画面。

三态对应 WallpaperService 的三个 mode：

| mode | 含义 | 谁在显示 |
|---|---|---|
| 2 | 桌面 | 系统桌面上的壁纸窗口 |
| 1 | 锁屏 | 锁屏壁纸窗口（Keyguard） |
| 0 | 息屏 / AOD | 转场期间是壁纸窗口；AOD 稳定后由注入到 AODView 的 TextureView 接管 |
| -1 | 未定 | 引擎刚创建时的初始值 |

用户能看到的功能族（详见第 5 节）：
- 照片壁纸：单张 / 锁屏+桌面两张 / 相框（前景照片 + 背景照片）
- 魅族静态壁纸：5 套内置 PhotoStyle（leave_light / moon / door / mountain 等）
- Cosmic 系列：30 多种程序化场景（宇宙、流体、光带……）
- Vivo 系列：液态、趣味光栅、闪卡，支持视频、主体遮罩、陀螺仪
- Flyme 视频壁纸、气泡、立体视差、渐变等
- 系统个性化入口里的 AliveHS 卡片、息屏样式里的「AliveHS 样式」

## 2. 硬约束（用户明确要求，改代码前必须遵守）

1. 禁止用「缩短动画 / 砍掉动画 / 一帧到位」的方式规避抽帧。动画本体必须完整播放。
   这条从 m07368 起一直有效，2026-11-14 用户再次强调。
2. 用户要 120fps 的顺滑感；曾经把帧率锁 60 被明确否决（「这是动画啊，锁到 60 帧是什么意思」）。
3. 删除任何「具体功能」的源码之前必须先问用户（m09551 原话）。
   删探针、删临时实验代码不算功能，但也应在交付说明里写清楚。
4. 「AliveHS 样式」是刻意设计的机制，不是 bug：
   平时隐藏；应用我们的壁纸后强制切到它并锁住触摸；它实际对应「和锁屏样式一致」的全屏 AOD。
5. 息屏画面「黑底 + 时钟 + 缩成球的壁纸」是预期效果，不是渲染失败。

check_xiaomi_desktop / check_xiaomi_aod_density / check_unlock_handoff / check_fingerprint_clock /

产物：dist/AliveHS-0.1.0-arm64-v8a.apk（约 307,315,022 字节，其中 244MB 是素材）
+ build-report.json + SHA256SUMS。

只在需要重编原生库时才要 Rust 1.96 + NDK r29；
平时用 ALIVEHS_NATIVE_SO 指向现成的 .tmp/build/libalive_clean.so 复用（467,592 字节，sha 23e25e3a…）。

### 3.5 常见坑

- 构建失败时 install 仍可能报 Success，装上去的是旧包。永远核对 classes.dex 的 sha256。
- 重装 8 次会触发 LSPosed 的「需要重启」提示；system_server / SystemUI 作用域的新代码要重启才生效。
- 模块连续崩溃会触发 LSPosed 安全模式，模块整个不加载。
- adb shell 多参数会被远端 sh 重新分词：带空格 / && / 引号的命令写成 .sh 推到 /data/local/tmp 再用 su -c 执行。
- killall com.android.systemui 之后 10 秒内截图拍到的是锁屏，不是 AOD。

## 5. 功能与机制详解

### 5.1 CleanWallpaper 状态机

常量（CleanWallpaper.java 第 11-23 行）：
- SETTLE_DELAYS = {0,80,160,280,450,700,1000,1400,1900,2500,3200} ms，SETTLE_LIMIT = 40
- WAKE_DWELL = 0，WAKE_POLL = 50ms，FINGERPRINT_WINDOW = 900ms
- HOME_GRACE = 1500ms

三种 input：
1. 系统广播：SCREEN_OFF → screenOn=false，ambient=true，panelDark=true，立刻 send(0,false)；
   SCREEN_ON / USER_PRESENT → screenOn=true，ambient=false，update() + settle()。
2. SceneChannel 推送：scene(mode, animate, time, phase, clockToken, nightLevel, aodMask)，
   touch / region / fingerprint / keyguardHiding / backdrop / disconnected。
3. 定时 settle：从 0ms 起按 SETTLE_DELAYS 连续重算，直到 state 稳定或 40 步。
   这是为了追 MIUI 自己的异步状态（锁屏 keyguard 状态常常晚几百毫秒才变）。

update() 的判据顺序（决定 mode）：
- 非预览且屏幕灭 → send(0,false)。
- mode = isPreview() ? 1 : scenesState.fallback(ambient, locked)。
- 从 0 回 1 且未 ambient：进 lockGrace，最多等到 fingerprint+FINGERPRINT_WINDOW 或解锁事件，
  再决定去 2 还是 1（避免「解锁瞬间先闪一下锁屏」）。
- mode==1 且上一态是 2 且离开桌面不到 HOME_GRACE → 抑制，保持 2。
- 最后 mode != lastSentMode 才 send(mode,true)。

send(mode, animate) 会打：
    scene send mode=X->Y animate=true visible=… wallpaper=… wasDark=…
这条日志是排查「动画丢了」的第一现场。

onCommand 里的关键修复（第 8 节）：处理 android.wallpaper.goingtosleep，
在系统真正灭屏之前就抢先起 2->0 过渡。没有这段，MIUI 会在灭屏前把状态改回 1，
最后只能瞬时跳到 0，用户看到的就是「动画丢了」。

### 5.2 RenderLoop 帧循环

- 用 Choreographer.postFrameCallback 驱动；帧回调里 framePosted=false，然后 handler.post(renderTask)。
- schedule() 只在「可见或有 forceFrame」且「有场景」且「没有已排队帧」时投递。
- 可见性：renderingVisible() 由 Engine 的 wallpaperVisible/renderVisible 决定；
  屏幕灭但 AOD 场景在跑时仍需出帧。
- 每帧流程：pacer.due(time) 判闸 → NativeScene.effects(...) → NativeScene.render(...)
  → swap()（eglSwapBuffers）→ 视情况 schedule() 下一帧。
- 场景种类三选一：scene（native 照片场景）、cosmic（Java/EGL 渲染器）、vivo（独立引擎）。
  三者互斥，createScene() 里按 SceneOptions 决定。
- 照片走 loadPhoto()：从 files 目录读，缺文件时生成一张渐变占位图（不会崩）。
- AOD 区域：AodRegion.parse(displayId, w, h, Settings.System "alive_wallpaper_position")
  → renderer.aodRegion(...)，用来让 AOD 的球在正确位置。

### 5.3 动效层

- SceneMotion：60 个 float 通道的显式时间线，COUNT=60，索引常量
  LENS=3、GLASS=13、GROUND=19、FULL=21、MASK=23、PHOTO_MATRIX=25、DECOR_MATRIX=41。
  values[0] 就是探针里的 v0：mode 0 场景权重（0→1 表示球化完成度）。
  时间线自管（不再是 AnimatorSet），带 STALL_STEP=24ms 钳制：掉帧时动画不会跳跃，
  只会整体慢一点。这一点和硬约束「不许瞬时到位」是配套的。
- TextureMotion / FrameMotion：照片纹理层与相框层的独立运动。
- CosmicMotion：cosmic 场景的进度与交互（点击触发 interaction）。
- AodMotionWindow：进 AOD 的 3000ms 运动窗口，leave() 关掉。
- WallpaperTransitionTime：统一的转场计时器（restart/pause/elapsed）。

### 5.4 场景族选型（WallpaperRenderer.create）

| cosmic 取值 | 渲染器 | 说明 |
|---|---|---|
| 401–403 | FlymeVideoRenderer | Flyme 视频壁纸 |
| 501–503 | StereoRenderer | 立体 / 陀螺仪视差（StereoSensor） |
| 201–205 | BubbleRenderer | 气泡 |
| 301–303 | GradientRenderer | 渐变 |
| 1,3,4,6–19,101–105 | CosmicRenderer | 程序化宇宙/流体等 |
| 0 | 无 | 走 native 照片场景 |

SceneOptions.supportedCosmic() 是唯一的合法性判据，新增号段要同步改这里。

### 5.5 照片与素材

- 用户选图 → PhotoSources（相册/文件）→ PhotoCropActivity（裁切）→ SceneOptions 存文件名。
- 相框：frame_photo + frame_pair + frame_x/y/size/angle，FrameCropActivity 编辑。
- 锁屏与桌面分开：lock + home 两个场景号，home_follow_lock 控制是否跟随。
- 文件白名单：photo / home_photo / frame_photo 只接受 files 目录下的文件名。
- 小米内置包：XiaomiBuiltinPacks 从 assets/xiaomi/packs.json 读分片（CHUNK_LIMIT=4MB），
  拼成 XZ 后在 files 目录还原成 apk 并校验 sha256。素材已按用户要求删除，代码骨架保留。

### 5.6 AOD（最容易踩错的一块）

链路：
1. 系统灭屏 → MIUI doze 起来 → com.miui.aod 的 AODView 被创建（实际代码以插件形式跑在
   SystemUI 进程里，类名仍是 com.miui.aod.*）。
2. HyperOsAod 在每个 AODView 构造后 attach(root)：找到内层 com.miui.aod.AODView，
   往里 addView 一个 AodSurface（TextureView，MATCH_PARENT，index 0），
   然后 new RenderLoop(context) + mode(0) + attach(surface)。
   当前 attach 只做一次 findInnerAod + 200ms 重试；HyperOsAod.supervise() 仍在源码里，
   但全仓库无调用点，是死代码（commit e2fd3fc 后停用），不要按「每 300ms 持续监管」理解。
3. 若注入不可用，AodOverlay 还有一条备路：type 2038 的 overlay 窗口。
   实测在当前系统上被 appop 策略抑制（isOnScreen=false），不要指望它。
4. AOD 期间 RenderLoop 用 mode(0)，照片来自 AodWallpaperProvider。

全屏 AOD 判定（这是「三方壁纸不支持」toast 的机械原因）：
SystemUI 的 com.android.keyguard.fullaod.MiuiFullAodManager：
- onWallpaperChanged() 里 isWallpaperTypeSupport = isDefaultLockScreenTheme()
  && isMiuiWallpaperComponentUsing() && !"super_wallpaper".equals(type)。
- 第三方 WallpaperService 让 isMiuiWallpaperComponentUsing() 恒 false
  → isWallpaperTypeSupport=false。
- updateSettings() 里 support = isLockScreenTemplateSupport && isWallpaperTypeSupport
  && isDeviceSupport && …；disable_reason 按位标原因，bit4 = 三方壁纸服务
  （toast 文案 2132018707）；support=0 时还会把 full_screen_aod_on 清成 0。

AodFullScreen 的六处 hook（SystemUI 进程，日志 force full aod: hooks=6；HEAD 未含未提交的
hookWallpaperType 时是 hooks=4）：
- com.miui.aod.Utils#isSupportFsAod / isInnerScreenSupportFsAod → true
- MiuiConfigs.SUPPORT_FULL_AOD / INNER_SCREEN_SUPPORT_FULL_AOD → true（反射，失败走 Unsafe）
- MiuiFullAodManager 构造后 isDeviceSupport=true
- MiuiFullAodManager#onWallpaperChanged / #updateSettings 执行前把 isWallpaperTypeSupport 强 true
  （只在壁纸是我们的时才强推，日志 force full aod: wallpaper type support）
→ 结果：full_screen_aod_support=1，disable_reason=0，toast 消失。

AodWallpaperMode 管 full_screen_aod_on 这个开关：
- 应用壁纸时 enter()：记住原值（alive_aod_restore_value / alive_aod_restore_set），写 1。
- restoreWhenForeign()：连续 5 次 × 1s 确认壁纸真的不是我们的，才还原。
  日志 aod restore cancelled after N miss / aod foreign confirmed x5。
  这是为了避免装包瞬间 getWallpaperInfo() 返回 null 就误还原。
- ensureEnabled()：壁纸是我们的、本来是我们开的、但值被清了 → 写回 1，日志 aod mode repaired ->1。
- 已知问题：开机早期 alive() 还没为真，MiuiFullAodManager 会把 on 清成 0；
  support/reason 稍后自己回到 1/0，但 on 不会自己回来。所以每次开机后可能需要在
  息屏设置页确认一次（或依赖 ensureEnabled，需验证触发时机）。

AodSettingsGuard 的「AliveHS 样式」：
- hook com.miui.aod.settings.SettingsView 的 onFinishInflate / updateState / updateSpinnerState。
- 取 aod_resting_screen_style 行的 spinner，把 adapter 换成 [原 item0, "AliveHS 样式"]，
  setSelection(1)，再锁死整行触摸。
- 历史 bug：MIUI 只建两个 spinner 项时 setSelection(2) 越界崩，已 clamp。
- 用户明确这是刻意机制，不要「修」成原生列表。

### 5.7 锁屏与桌面联动

- KeyguardTouchRelay：液态样式下把上滑解锁限制在屏幕底部约 12%（88% 以下），
  通过 SceneChannel 的 Messenger 与壁纸进程通信。
- KeyguardDepthHider：我们的壁纸在时隐藏 MIUI 的景深图层，避免双份人像。
- HomeActivationStatus：设置页里显示「桌面是否在用我们」与「模块是否激活 / Root 是否授权」。
- HomeEntryActivity：个性化入口用的透明窗口 Activity，套 MIUI 的 windowAnimationStyle，
  点进去像系统原生页面。

### 7.3 探针（上线前必须删）

RenderLoop 里三处：
- probe frame dt=…（vsync 节奏）
- probe vsync gap=…（>25ms 才打）
- probe draw gap=… eff=… ren=… sw=… mode=… v0=…
  字段：probeUntil / probeLast / probeVsyncLast / probeDrawLast
  进入 mode 0 时开始 1500ms 采样。

判读：
- eff = NativeScene.effects 耗时；ren = NativeScene.render；sw = eglSwapBuffers。
- gap 是「上一帧开始绘制到这一帧开始绘制」的时间，跨帧掉帧会直接体现在这里。
- v0 是 SceneMotion.values[0]，0→1 表示球化进度。历史数据显示 ren 长耗时集中在
  v0≈0.0738 / 0.1383 / 0.0045 这几个位置。

### 7.4 判断卡顿归属

1. 我们的 eff/ren/sw 都 <5ms，gap 却 >100ms → 不是我们算得慢，看下一帧是否被 vsync 拖住。
2. sw 单次 200ms+，且同一时刻 SurfaceFlinger 打 drawWallpaperAnim / Wallpaper-Anim: progress
   几乎不动 → SF 被压住，我们是受害者。
3. ren 单次 120–160ms，CPU ticks 不涨、GPU 未打满 → 驱动/同步等待（见 10.1）。

## 10. 下一步：降低渲染压力（重点）

### 10.1 已经排掉的假设

- Vulkan 换后端：没有意义。我们的 eff/ren/sw 都是 0–4ms，瓶颈不在我们的 GL 调用；
  换后端不会改变 SF 每帧对全屏壁纸层做模糊+压暗的成本。
- 我们侧 CPU 太慢：不成立。136ms 阻塞窗口里进程 CPU ticks 每 20–40ms 只涨 0–2。
- GPU 打满：不成立。gpubusy 峰值 67% / 81% / 83%（480/480/422MHz），没有饱和。
- shader 编译 / 纹理上传：不成立。capstone 反汇编 alive_scene_render（0x3601c，760 条指令）
  只有 uniform 设置 + 3 次 glDrawArrays，没有 glCompileShader / glLinkProgram / glTexImage2D。
- glFinish / glFlush / glReadPixels / glFenceSync：原生库里根本没有这些导入。

### 10.2 已定位的真实瓶颈

1. SurfaceFlinger 每帧对壁纸层做全分辨率（1200x2608）处理：
   makePassBlurBetterDownShader（layers:1，第二层是 VRI-NotificationShade）、
   drawWallpaperAnim（enableWallPaperAnim=1，process=动画进度）、shaderName=yahei。
2. 转场期间同一屏上存在两个全分辨率渲染循环：
   - 壁纸进程（pid 3328 一类）：mode 2→0 过渡
   - SystemUI 内的 AOD loop（pid 3603 一类）：mode 0 注入场景
   两者都在 120fps 时，SF 每帧要消费两倍的 buffer 提交。
3. 对照实验（决定性）：
   - 120fps：25 次 sw=245–276ms，壁纸进程与 SystemUI AOD loop 同一毫秒成对卡住；
     SF 自己的 Wallpaper-Anim 进度出现 250ms 断档。
   - 60fps（DOZE=16ms）：sw≥80ms 事件 0 次，250ms 停摆全部消失，只剩跨轮空档。
   → 停摆由「转场期间的高帧率渲染压力」触发，不是某一次调用慢。

### 10.3 可以做的方向（按性价比排序）

A. 先量清楚「静止的 AOD 到底出了多少帧」，再决定是否要做静止帧去重
   现状绘制条件（RenderLoop.render，第 389-411 行）：
       boolean moving = textureMotion.active() || motion.transitionActive()
                     || (frameMotion != null ? frameMotion.active()
                        : mode == 0 && (preview || sailContinuousAod || aodMotion.running(time)));
       if (forced || pacer.due(time) || !moving) { 画一帧 }
       if (moving || frameSample.pending || resumedSample || forced) schedule();
   注意 !moving 分支是「补一帧然后不再排帧」：静止后 loop 会自己停，不是每个 vsync 都重绘。
   所以先测量：让设备在 AOD 停 60 秒，数 probe draw 的行数。
   已知干扰项：aodMotion.running(time) 在进 AOD 后有 3000ms 窗口（AodMotionWindow），
   这段时间 moving 恒 true，会一直出帧；14:26 那次「连续 16ms 出帧」就落在这个窗口里。
   如果 60 秒里仍持续出帧，说明有别的路径在反复 poke/schedule（时钟回调、可见性抖动、
   supervise 重挂），那就值得加 dirty 门控：只有场景在动、时钟秒变化、通知/电量变化、
   触摸、可见性变化、强制帧才重绘。
   验证：probe draw 行数应大幅下降；screencap 对比时钟是否正常跳动。

B. 转场期间只保留一个渲染器
   转场时壁纸进程画 mode 2→0，同时 SystemUI 的 AOD loop 也在画 mode 0。
   若注入的 AodSurface 在转场期间实际不可见（现有证据指向这一点），
   那这段时间 AOD loop 是纯浪费。
   做法：AodSurface 的 loop 增加「AOD 视图真正可见」判据（onVisibilityAggregated /
   isShown + 窗口可见），不可见就不 schedule。
   预期：SF 每帧少消费一个 1200x2608 buffer，250ms 停摆概率下降。
   风险：AOD 首帧可能晚一拍 → 需要预留一帧预热（先画一帧再停）。

C. AOD 阶段降低缓冲分辨率
   AOD 画面是「黑底 + 时钟 + 缩成球的壁纸」，细节远少于桌面。
   把注入 surface 的 buffer 降到 0.5x（600x1304），显示时由 GPU 拉伸。
   视觉验证：A/B 两版截图逐像素对比，若肉眼无差异再采纳。
   这条动的是画质，必须先给用户看对比图，不能擅自改。

D. 核对 enableWallPaperAnim 的来源
   SF 的 drawWallpaperAnim 是 MIUI 转场动画本体（缩成球），按硬约束不能动。
   但值得确认它是不是被我们强开 isWallpaperTypeSupport 之后才出现的；
   若是，说明全屏 AOD 与这层 blur 是绑定的，只能在别处省。

E. 帧率策略作为兜底
   mode 0 用 60fps（DOZE_INTERVAL_NS=16ms）已被证明能消掉 250ms 停摆，
   用户可以接受吗？目前看是否决的（「这不是解决办法」）。保留为可回退开关。

### 10.4 建议的执行顺序

第 1 步（1 小时）：先把 A 量清楚（AOD 静止 60 秒的 probe draw 行数 + 谁在 poke）。
  数据说话：如果静止后本来就停了，A 直接划掉，省得白改；如果没停，再上 dirty 门控。
第 2 步（半天）：做 B（转场期间停掉不可见的 AOD loop），用现有探针量 sw≥80ms 的次数。
第 3 步：拿 A+B 的结果找用户复测。若仍有 250ms 停摆，再讨论 C（要视觉对比图）。

每一步的验收标准：
- probe draw 的 gap p99 ≤ 20ms（转场段）
- sw≥80ms 事件 0 次 / 6 轮息屏
- SF 的 Wallpaper-Anim 进度无 ≥100ms 断档（跨轮空档除外）
- 动画完整跑完：scene send 全部 animate=true，首帧 v0 从 0 起，时长 800–1300ms

### 10.5 还要补的取证

- 用 simpleperf 采 SurfaceFlinger（pid 会变），必须确保采样窗口里真的有转场：
  先看 logcat 里出现 Wallpaper-Anim: progress 行再开始采，否则采到的全是空转。
- 首帧 ren=150ms：在 alive_scene_render 的三次 glDrawArrays 之间插时间戳做不到（无源码），
  替代方案是 perf 采样 AOD 进程，看 150ms 窗口里驱动符号的占比；或试
  eglSwapInterval / 提前一帧预热（先画一帧到 1x1 FBO 强制驱动初始化）。
  验证「首次使用程序对象懒编译」假设的最小实验：进入 AOD 前先做一次 1x1 预绘制，
  若首帧 150ms 消失，则假设成立。

## 13. AOD AliveHS 机制修复（2026-11-14 晚）

后续会话已按用户本意重做 AOD 样式机制，详细记录见 `docs/port/AOD-ALIVEHS-20261114.md`。关键变化：

- `AodWallpaperMode.alive()` 只认系统（home）壁纸；静态系统壁纸的 `getWallpaperInfo()==null` 必须视为“不是本项目”，不再 fallback 到锁屏壁纸，避免 AOD 关闭后仍显示 overlay、景深双上层和指纹时钟异常。
- `AodOverlay`、`KeyguardDepthHider` 统一使用该判定；`KeyguardDepthHider.apply()` 在非本项目壁纸时直接返回，不再调用 MIUI 景深方法。

- `AodFullScreen` 只在项目壁纸时条件化 hook `isSupportFsAod` / `isDeviceSupport` / `isWallpaperTypeSupport` / `MiuiConfigs` flags；系统壁纸时恢复原值。
- 设置页 `AodSettingsGuard` 包装原生 adapter，项目壁纸时显示/锁定 AliveHS，系统壁纸时 unbind 恢复。
