# 开发硬性要求（AI 与人类都要遵守）

> 本文件是**规则清单**，不是叙事。凡是"必须/禁止"的条目，都是用户明确要求或已踩过坑后定下的。
> 需要可直接粘贴的开工提示词见 `ai/01-AI协作提示词.md`；原始要求原文见 `../00-原始要求与协作规则.md`。

## 1. 总原则

1. **质量第一**：用户明确说"你的时间和 token 预算是无限的，可以随时进行深度思考，始终将质量放在第一位"。不为省时间跳过复现、日志、回归。
2. **客观优先，不迎合猜想**：用户说"对我的猜想或要求等，不要轻易认同，须先进行完全客观的分析"。结论只给三种：**支持 / 不支持 / 证据不足**。用户的因果假设不成立时直接说明并给替代解释。
3. **证据先于说法**：没有原始证据的结论一律降级为【证据不足】；截图能证明的标【支持】；有 logcat/数值的标【实测】。
4. **先看再改**：改任何代码前先读相关实现与项目约定；不引入无关变动。
5. **可回滚**：任何改动都要能回退（git 提交、`dist/save` 存档、文档写清回退方法）。

## 2. 工作目录与 git

1. 工作区根目录按用途划分：`app/`（源码与资源）、`tools/`（脚本）、`docs/`（文档）、`native/`、`dist/`（产物）、`.tmp/`（一切临时物）。
2. **源码目录不得混入无关文件**（逆向产物、探针、截图、临时脚本）。逆向与反编译材料放 `.tmp/research/`。
3. 一切中间产物放 `.jxai/tmp/<会话id>/` 或 `.tmp/` 分类目录，不要散落在项目里。
4. **不要 `git add -A`**：代码与文档分两个提交；只 add 明确属于本次改动的路径。
5. 提交信息用中文或英文均可，但要说清"改了什么、为什么"；一个提交只做一件事。
6. 分支与远程已分叉时，推送前先 `git_sync` 拉取合并；`git push` 首次失败先重试一次（凭据常在首次推送时才刷新）。

## 3. 证据与验证

1. 每条重要结论必须能回答：**证据在哪**（文件:行号、logcat 原文、截图路径、哈希）。
2. 不接受"改了现象就变"当因果：现象变化可能来自别的变量。要证明因果，用**逐帧/逐点数值**（如 `ratio=0.43→0.11`）或**差分实验**（改回原样看是否复原）。
3. 优先"哪些情况是好的"这种差分事实来缩小范围（本项目多次靠用户给的差分事实一次定位）。
4. A/B 实验优先于对着代码猜：整文件 `git checkout <基线> -- <file>` 一次判定方向。
5. 无效改法**一律回退**，不留半成品；回退后重建哈希要与基线一致。

## 4. 构建与装机

1. 构建必须带这四个环境变量（PowerShell 示例）：

```powershell
$env:JAVA_HOME='C:\Users\ybybabab\app\pcl\JAVA21\graalvm'
$env:ANDROID_HOME="$env:LOCALAPPDATA\Android\Sdk"
$env:ANDROID_SDK_ROOT=$env:ANDROID_HOME
$env:PYTHONIOENCODING='utf-8'
$env:ALIVEHS_NATIVE_SO='.tmp/build/libalive_clean.so'
python tools\build_release.py --no-checks
```

2. **漏 `ALIVEHS_NATIVE_SO` 会 `FileNotFoundError: [WinError 2]`**；`check_layout.py` 当前缺脚本且引用已删类，**必须 `--no-checks`**。
3. **判断构建成功不能只看 `sha=`**：要检查输出里有没有 `error:` / `错误:` / `Traceback`。javac 失败时 `dist/SHA256SUMS` 仍是上一版哈希。
4. 产物归档：`dist/save/<sha256前7位>.apk`，复制后**重算哈希比对**，并维护 `dist/save/SHA256SUMS`（用 Python 重算，不要手写）。
5. 装机后**三方比对**：设备侧 `su 0 sha256sum <apk路径>` = 本地 `dist/SHA256SUMS` = 用于提交的源码构建结果。
6. 构建时间取 `Get-Item` 的 `LastWriteTime`，**禁止编造时间**（曾因编时间被用户质问）。

## 5. 设备操作

1. **危险操作默认禁止**：`setprop`、改系统属性、`settings put`、删/替换系统文件、格式化。只读观察（`dumpsys`/`settings get`/`screencap`/`logcat`）随时可以。
2. 任何系统级或不可逆改动，**必须先写** `history/02-系统变更与危险操作记录.md`（日期、键、原值、新值、原因、恢复情况）。
3. 已确立的设备限制与套路见 `facts/02-平台既定事实.md`，其中高频几条：
   - **adb 不能解锁有 PIN 的设备**：`input swipe`/`keyevent 82`/`wm dismiss-keyguard` 无效 → 需要解锁态的验证必须请用户配合。
   - 装包后免重启加载：`su 0 killall com.android.systemui` + `su 0 killall org.aliveclean`（需整机重启的只有 system_server 相关 hook）。
   - 改 `scene.xml` 做 A/B：备份 → 本地改 → `adb push` → `su 0 cp` 覆盖 + `chown u0_a530:u0_a530` + `chmod 660` → `killall org.aliveclean`。
4. 未导出的 Activity 用 `su 0 am start -W -n <pkg>/<activity>` 才能从 adb 启动。

## 6. 日志与探针

1. 发布包 `Diagnostics.TRACE` 必须为 `false`；诊断代码用完**必须删干净**（`grep` 残留计数为 0 才算清完）。
2. 临时自检入口（BroadcastReceiver 之类）发布前必须连同 `AndroidManifest.xml` 的声明一起删除。
3. 保留"每次操作打一行"的低频日志（如 `photo decode ... 269ms`）是有价值的，但禁止每帧打印。
4. 高频日志会让 logcat 淹没关键行，排查时先 `logcat -c` 再复现。

## 7. 文档维护（实时更新）

**每次**构建、安装、复测、bug 状态变化、功能变化，都要更新对应文档：

| 改动 | 必须更新 |
|---|---|
| 新构建/装机 | `history/01-版本与回归历史.md`（构建号/SHA/大小/时间/变化/验证状态/存档路径） |
| 修好或新发现 bug | `troubleshooting/02-已定位Bug档案.md`（现象/取证/根因/修法/验证/回退）；症状级条目补到 `troubleshooting/01-症状排查手册.md` |
| 新功能或实现变化 | `features/*`（含关键代码块与文件:行号） |
| 系统级/不可逆操作 | `history/02-系统变更与危险操作记录.md` |
| 新确立的平台事实 | `facts/02-平台既定事实.md` |
| 目录/依赖/构建方式变化 | `build/01-构建安装测试.md`、`history/03-代码地图与数据流.md` |

格式约定：

- `.md` 一律 **UTF-8**；`history/01-*` 是 **UTF-8 带 BOM + CRLF**，改动时不要破坏（用 Python 读写 `utf-8-sig` + 显式 `\r\n`，或用 `edit` 工具）。
- 不要用 `Set-Content -Encoding UTF8` 批量改 Markdown（会动行尾、可能丢 BOM）。
- 新文档要登记到 `docs/kb/README.md` 的索引表。
- 不要在聊天里替代落盘：**只在聊天里汇报、不写文档 = 没做**。

## 8. 汇报格式

1. 先给结论（修好没有、证据是什么），再给细节。
2. 如实报告失败：命令失败、编译报错、测试不过时给真实输出与原因，**绝不编造结果**。
3. 明确区分：已验证 / 未验证 / 证据不足。
4. 交付物要给绝对可点的路径与哈希。

## 9. 反模式清单（这些坑都踩过）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 编造构建时间/日志 | 用户当场识破，信任崩塌 | 时间取文件时间戳；日志只贴真实输出 |
| 只看 `sha=` 判断构建成功 | 拿着上一版 APK 装机验证新代码 | 检查 `error:`/`Traceback` |
| 改了现象就当修好 | 动画一起没了、双层搬家 | 逐帧数值 + 差分实验 |
| 在生产包留调试日志/探针 | 用户发现"调试用的没删" | 发布前 grep 残留计数为 0 |
| 用 `ImageDecoder` 处理大图 | 1 秒级卡顿（见 `features/06-*`） | 用 `PhotoDecode`（BitmapFactory 采样） |
| 用 PNG 存照片 | 每张 1.7–2.6s | 复制原图或 JPEG |
| PowerShell 多行 `-m` 传中文 | `error: switch 'm' requires a value` | 写临时文件 + `git commit -F` |
| 一次 `git add -A` | 把 `.tmp`、产物、逆向材料卷进提交 | 按路径分别 add |
| 用子代理处理高度耦合的历史问题 | 二次幻觉 | 自带全部上下文的子对话，或自己做 |

## 9.1 注释与死代码（2026-11-16 起）

1. 每个**顶层类型**必须有类级注释：一句职责 + 只在必要时写第二段（平台约束/时序/历史坑，历史坑要给文档路径与 §编号）。细则见 `../build/02-代码注释规范.md`。
2. 注释与代码冲突时**以代码为准改注释**；不允许留着不成立的注释。
3. 死代码删除必须有 grep 证据（含字符串与反射取用）；反射目标、Manifest 组件、`native` 方法、`@Override` 空实现、吞异常的 `catch` **不许删**；拿不准的只报告。
4. 注释改动与逻辑改动**分开提交**，前者用 `git diff --numstat`（deletions 必须为 0）自证。
5. 删了成员要用 `python tools/compare_apks.py <旧> <新> --allow-gone <类#成员>` 证明"只少了该少的"。

## 10. 提问的分寸

- 能自己查到的事实**不要问用户**（日志、代码、版本、哈希）。
- 影响面小、有合理默认的问题：短超时（30s）问，未答按默认继续。
- 决定方向、错了无法回头的确认：`timeout_sec=0` 一直等。
- 用户在做验证时，问题要写清"要做什么动作、做到哪一步、回来告诉我什么"。

## 11. 子代理使用（2026-11-16 起）

- 可以派发子对话（`dispatch_sub`），但子对话**只有一级**、默认看不到本对话记录：任务书必须自包含（目标、验收标准、涉及目录、禁止事项）。
- 需要它继承上下文时用「继承上下文子对话」专家，任务里只写"接下来做什么"。
- 高度依赖历史细节的排查任务，自己做比派发更快更准。
