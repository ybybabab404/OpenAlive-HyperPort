## 3. 从初始要求推导出的硬规则

### 3.1 工作目录

- 源码目录 `app/` 只放源码、资源、构建脚本允许的内容。
- 逆向 APK、反编译目录、探针日志、截图、临时脚本放 `.tmp/` 对应分类。
- `.tmp/` 分类：`build/`、`artifacts/`、`research/`、`logs/`、`screenshots/`、`scripts/`、`archive/`、`scratch/`。
- 不把 `workbench/` 的逆向材料移进 `app/`。
- 所有改动可回滚，使用 git；提交前检查 `git status`，不要误提交 `.tmp/` 大文件。

### 3.2 文档不可尽信

任何交接文档、旧总结、team 报告、代码注释都可能过时。采用前至少做一项交叉验证：

- 代码/资源当前是否存在；
- `git log`/diff 是否支持该说法；
- APK 哈希与设备安装是否一致；
- 设备 `settings get`、`dumpsys`、logcat、截图是否支持；
- 旧文档的 SHA/行号/类名是否仍存在。

冲突时不要“选一个看起来合理的”，而是记录冲突，继续查。

### 3.3 手机危险操作

以下操作默认禁止，除非用户明确授权并记录到 `09-系统变更与危险操作记录.md`：

- `setprop`、修改系统属性、SELinux、权限数据库；
- 删除/替换系统 APK、系统配置；
- 永久改 `settings put`（尤其 `full_screen_aod_on`、`aod_show_style`）；
- 格式化、清 data、卸载系统应用；
- 写入 `/system`、`/vendor`、`/product`。

允许的临时测试也必须：

1. 先记录原值；
2. 测试后恢复；
3. 在 `09-*` 写日期、键、原值、新值、原因、恢复情况；
4. 不把“临时测试”说成“已永久修改”。

### 3.4 客观分析，不迎合猜想

用户明确说“不要轻易认同我的猜想”。正确做法：

- 先复述用户观察，不急着下结论；
- 用代码/日志证明或证伪；
- 给出“支持/不支持/证据不足”三种结论；
- 如果用户的因果假设不成立，直接说明，并给出替代解释；
- 不用“可能”“应该是”掩盖没有验证的事实。

### 3.5 质量优先

- 时间/token 不是限制；不允许为了快而跳过复现、日志、回归。
- 先保证正确性，再考虑性能/优雅。
- 一个修复必须说清楚：改了什么、为什么、怎么验证、还有什么风险。
- 不能把“转场帧有球”当成“稳定息屏有球”；不能把“旧版本通过”当成“当前版本通过”。
