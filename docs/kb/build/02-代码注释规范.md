# 05b 代码注释规范

> 2026-11-16 定版。起因：136 个 Java 文件里只有 12 个能说明自己是干什么的，
> 而本项目大量依赖"为什么这样做"的隐性知识（hook 为什么不能写设置、为什么必须走 root、为什么取样源要跟着目标层）。
> 本文件是规矩，不是建议；新代码与改动都按此执行。

## 1. 写什么

每个**顶层类型**（class / interface / enum）必须有类级注释，一到三句：

```java
/**
 * 一句话：这个类型在系统里承担什么职责。
 *
 * <p>第二段只在"看代码看不出来"的时候写：约束、易错点、为什么不能用更直觉的做法。</p>
 */
```

- 第一段回答"它是什么/它负责什么"，不要复述类名。
- 第二段只在有真实原因时写，常见的三类：
  1. **平台约束**：写设置会被 MIUI 改回去；只有 uid 1000 能调这个 API；这个构造签名被反射调用不能改。
  2. **时序/并发**：必须 post 到同一个 handler；同一槽位的 Track 后者覆盖前者；跨开机锁屏窗口要缓存实例。
  3. **历史坑**：某处看似冗余的校验是为了挡住某个已发生过的问题——**必须给文档路径与 §编号**，不要复述整段历史。

## 2. 不写什么

| 不写 | 原因 |
|---|---|
| `@author` / `@since` / `@version` | 无信息量，git 里有 |
| 参数/返回值逐条罗列（显而易见的） | 噪声；真正的约束放第二段 |
| "TODO 以后优化" 这类没有落点的愿望 | 要么写进 KB 待办，要么不做 |
| 与代码不一致的描述 | 比没有注释更糟：**注释与代码冲突时以代码为准并改注释** |
| 逐帧/逐字段的调试说明 | 调试代码用完就该删（见 §4） |

## 3. 方法与 inline 注释

- 方法注释只加在"看名字猜不到行为"的地方，例如：
  - `AodWallpaperMode.capture()`：为什么只记录不写设置；
  - `RenderLoop.mode()`：为什么不能用 `scenesState.mode()` 当判据；
  - `SceneMotion.prepare()`：为什么两条转场必须逐字同参数。
- 单行注释上限 110 字符；**不重排既有注释、不改代码格式**（避免与本次改动无关的 diff）。
- 报错信息用中文、给可执行的下一步（"请检查 Root 是否可用"），不要只写英文缩写。

## 4. Rust 侧

- 每个模块用 `//!` 写模块职责（`math.rs` = 纯矩阵数学；`gl.rs` = GLES 声明与薄封装；`renderer.rs` = 帧图）。
- 生成文件（如 `native/frame_rear.rs`）在文件头注明"由哪个脚本生成、不要手改"。
- `shaders.rs` 是厂商着色器原文，**不加注释、不改动**（版权与可追溯性原因）。

## 5. 死代码的判定（与 §6.1"探针必须删干净"配套）

**可以删，且必须有证据**（每条都要能贴出 grep 命中行）：

1. `private`/包内成员在全仓零引用（**含字符串与反射按名字取用**）；
2. 空方法体且不是 `@Override`、接口契约、生命周期回调；
3. 整个类零引用（同样要过字符串检查，注意 `"org.aliveclean.XxxAdapter"` 这种反射构造）；
4. 大段注释掉的旧代码——先把它承载的有效说明提炼进注释或 KB，再删代码；
5. 未使用的 `import`、未使用的常量、写完从不读的字段。

**不许删**（即使看着没用）：

- 反射/字符串类名目标、`Xp.hook*` 的目标方法、`AndroidManifest` 声明的组件、资源里引用的键；
- `native` 方法、`@Override` 的空实现、`catch (Throwable ignored) {}`（吞异常是有意的）；
- 任何"删了可能改变行为"的东西——**拿不准就只报告，不执行**。

## 6. 验证手段

| 目的 | 做法 |
|---|---|
| 只加注释、没动代码 | `git diff --numstat` 该文件必须是 `N 0`（deletions = 0） |
| 删成员后行为不变 | `python tools/compare_apks.py <旧.apk> <新.apk> --allow-gone <类#成员>`，输出 `no unexpected structural difference` 才算过 |
| 注释里的路径/编号真实存在 | 引用文档给 `docs/kb/...`、引用资源给 `app/assets/...`，并在改动时确认文件存在（2026-11-16 就抓到过把 `gradient.vert` 写成 `gradient.frag`） |
| 注释与代码一致 | 注释里凡出现数值、类名、文件名的断言，落地前对照代码核一遍 |

## 7. 一次改动的提交粒度

- 注释改动与逻辑改动**分开提交**（前者便于用 `--numstat` 验证 deletions=0）。
- 死代码删除单独一个提交，提交信息里逐项列出"删了什么、为什么零引用"。
