## 1. LSPosed 作用域与生效方式

### 1.1 作用域集合：四个，不要多也不要少

- 【已验证】模块声明的作用域只有四个：`com.android.systemui` / `com.miui.aod` / `com.android.thememanager` / `system` —— `tools/build_release.py` 里硬编码写入 `META-INF/xposed/scope.list`；`app/res/values/strings.xml` 的 `xposed_scope` 一致；APK 内 `module.prop` 为 `minApiVersion=102 / targetApiVersion=102 / staticScope=true`。
- 【已验证】**不要勾「安卓系统」(`android`)**：模块自己在 `onPackageLoaded` 里对 `"android"` 直接 `return`，勾了不会安装任何 hook，只扩大注入面与 LSPosed 安全模式风险 —— `app/java/org/aliveclean/CleanHooks.java` `onPackageLoaded()`；规则原文见 `troubleshooting/03-*` §1.2。
- 【已验证】**只需要「系统框架」`system`**：`system_server` 里的活由 `onSystemServerStarting` 进（不走 `android` 包）；UI 侧由三个具体进程作用域承载 —— `CleanHooks.java` 两个入口 + `troubleshooting/03-*` §1。
- 【已验证】中文界面按**包名**认，不按名字猜：「系统框架」=`system`，「安卓系统」=`android` —— `troubleshooting/03-*` §1.2（用户明确要求记录）。
- 【已验证】只声明了这四个不等于设备上真勾了这四个；LSPosed 里的实际勾选只能在设备上确认 —— `troubleshooting/03-*` §1.2 末尾。
- 【已验证】`module.prop` 的 `staticScope=true` 表示作用域集合是**静态声明**：要改作用域集合只能改构建脚本重新出包，运行时不能动态增删 —— `tools/build_release.py`。
- 【已验证】模块日志 tag 只有四个，`logcat -s AliveHS*` 一次就能全抓：`AliveHSHooks`（模块加载/hook 安装）、`AliveHSAod`（AOD 注入）、`AliveClean`（壁纸/渲染引擎）、`AliveHS`（全屏 AOD 等）—— `CleanHooks.java`、`troubleshooting/02-*` §9.5、`build/01-*` §7.3。

### 1.2 哪个 hook 装在哪个进程

| 进程（作用域） | 装的 hook | 出处 |
|---|---|---|
| `system_server`（`system`） | `AodWallpaperModeHook`（壁纸/用户变更 → capture/restore）、`DeviceIdleDelayHook`（`DEFER_MS=1200L`）、`IPackageManagerBase.checkPermission` 与 `PackageManagerService.checkPermission`（放行 `org.aliveclean` 的 `AMBIENT_WALLPAPER`）、`WallpaperInfo.supportsAmbientMode` | `CleanHooks.handleSystemServer()` |
| `com.android.systemui` | `AodFullScreen.install(loader,false)`、`ModuleActivationHook`、`HyperOsAod.install`（AODView 构造 hook + 注入）、`HyperOsAod.installDoze`、`KeyguardTouchRelay`、`KeyguardDepthHider`、`WallpaperInfo.supportsAmbientMode` | `CleanHooks.handle()` |
| `com.miui.aod` | `AodSettingsGuard`、`AodPreviewHider`、`AodWallpaperPreview.install`、`AodFullScreen.install(loader,true)` | 同上 |
| `com.android.thememanager` | `PersonalizeEntry`、`AodWallpaperPreview.installThemeManager` | 同上 |
| 其它进程 | 无 | 同上 |

- 【已验证】`AodFullScreen` 在 **systemui 与 miui.aod 各装一次**（`false`=SystemUI 侧，`true`=AOD 设置页侧）：漏勾 `com.miui.aod` 时设置页能力补不足，表现为样式行缺失/不生效 —— `CleanHooks.handle()`；`troubleshooting/03-*` §1.1。
- 【已验证】模块日志出现 `loaded into <包名> pid=`、`full aod hooks=`、`tm uf hook count=` 这类行才算真的加载；一条都没有就先查作用域/重启，不要改代码 —— `troubleshooting/03-*` §1.3。

### 1.3 API 102 的生效方式（哪些能免重启）

- 【已验证】`com.android.systemui` / `com.miui.aod` / `com.android.thememanager`：`su 0 killall <进程>` 即生效，**不需要重启手机** —— `history/02-*` §1、§8.6（`ff49027` 用 `killall com.android.systemui` 加载成功）；`troubleshooting/03-*` §2。
- 【已验证】`system`（system_server）：**必须整机重启**；只重启 SystemUI 不会让 system_server 重新加载模块 —— 同上；`facts/01-*` §2.1。
- 【已验证】`am force-stop com.android.systemui` 有时不换 PID（历史 PID 32258 未变，导致 AOD 关闭测试误判）；改用 `killall`，并用 `ps -A | grep systemui` 确认新 PID，必要时 `su 0 kill -9 <pid>` —— `history/02-*` §3.4；`troubleshooting/03-*` §2.1。
- 【源码事实】模块实现了 API 102 的 `onHotReloading` / `onHotReloaded`（unhook 旧句柄、按进程重装 hook），原则上支持 LSPosed 热重载；设备上是否实际走过热重载路径没有记录 —— `CleanHooks.java`。
- 【已验证】"不用重启手机"≠"不用重启进程"：装完 APK 后旧进程仍跑旧 dex，验证前必须确认进程已换 —— `troubleshooting/03-*` §2。
- 【历史】`killall com.android.systemui` 之后 10 秒内截图拍到的是锁屏，不是 AOD —— `docs/port/HANDOVER-20261114.md:120`。

### 1.4 怎么反查"作用域到底加载了没有"

- 【已验证】LSPosed 框架日志在 `/data/adb/lspd/log/`（`modules.log`、`lspmod.log`）；`adb logcat -s LSPosedFramework` 也能看到加载记录。每次"勾作用域/重启"后应把日志落盘到 `.tmp/logs/`（按日期命名），不要只写结论 —— `troubleshooting/03-*` §1.3、§1.4。
- 【历史】反查方法：在 `lspmod.log` 里按进程段 `(system)` / `(com.android.systemui)` 统计 `org.aliveclean` 行数。2026-11-14 15:51–15:54 那份日志里 `(system)` 段 515 行全是别的模块、`org.aliveclean` 在 `(system)` 为 **0 行**，而 systemui(33) / miui.aod(12) / thememanager(7) 都有 —— `troubleshooting/03-*` §1.4。
- 【历史】同一天上午（2026-11-15 10:2x）的日志里出现过 `(system)[org.aliveclean,AliveHSHooks,…] device idle: no-activity armed`，说明 `system` 作用域确实能加载本模块 —— 同上。两条合起来说明：**"没生效"要先用日志区分"没勾"和"没重启"**。
- 【已验证】`com.android.systemui` 进程内还有 `ModuleActivationHook` 与 `ModuleActivationProvider`（authority `org.aliveclean.clock.runtime`，`directBootAware="true"`）用于回执模块是否活着 —— `app/AndroidManifest.xml`；`CleanHooks.handle()`。

## 2. 设备事实

- 【已验证】机型 Xiaomi `25102RKBEC`，代号 `myron`，serial `9eb96e8a` —— `facts/01-*` §2；`history/02-*` §1。
- 【已验证】系统 HyperOS `4.0.0.33.XPMCNXM` / Android 17（SDK 37）/ LSPosed API 102 —— `troubleshooting/02-*` §9.1 实机快照。
- 【已验证】屏幕 1200×2608 @ 480dpi —— AOD 日志 `T05 texture#available id=… 1200x2608`（`troubleshooting/02-*` §9.5）；截图分辨率一致。
- 【已验证】有 root：`su 0`（root）、`su 1000`（system uid）都可用，`SceneApply` 就靠 `su 1000` —— `build/01-*` §4。
- 【已验证】**本机原生不支持全屏 AOD**：`MiuiConfigs.SUPPORT_FULL_AOD` / `INNER_SCREEN_SUPPORT_FULL_AOD` 静态值初始为 `false`（日志 `full aod flags initializer alive=false: SUPPORT_FULL_AOD=false`）；所以"全屏 AOD / 和锁屏样式一致"这个能力是**模块补出来的**，不是系统自带 —— `app/java/org/aliveclean/AodFullScreen.java:465` 注释 + `troubleshooting/02-*` §11.2。
- 【已验证】`full_screen_aod_on` / `doze_always_on` 都是 `Settings.Secure` 键：前者=用户选的「和锁屏样式一致」(1) 或「自定义」(0)，后者=用户"息屏显示"总开关。新版模块**只读不写** `full_screen_aod_on` —— `AodWallpaperMode.java` `wantsFullAod()`/`enter()`；`history/03-*` Secure 键表。
- 【已验证】AOD 画面本来就是「黑底 + 顶部球 + 日期时钟」；注入层的球参数是 `BALL_CENTER_Y=0.165`、`BALL_RADIUS=0.22` —— `HyperOsAod.java:29-30`；真机实拍与之一致（`troubleshooting/02-*` §12.9）。
- 【已验证】`AODView` 实例**整机只构造一次**：开机后第一段锁屏时构造，之后每次息屏复用，不是每次息屏新建 —— `troubleshooting/02-*` §9.5。
- 【已验证】开机完成判据：`adb shell getprop sys.boot_completed` 返回 `1`；`reboot` 后要 `wait-for-device` 再查 —— `build/01-*` §3.2。
- 【已验证】"壁纸是不是我们的"只能看 system 槽：`dumpsys wallpaper` 的 `mWallpaperComponent` 为 `org.aliveclean/.CleanWallpaper` 才算；系统静态壁纸时 `WallpaperManager.getWallpaperInfo()` 返回 `null`，`AodWallpaperMode.alive()` 自然是 false（这不是 bug）—— `troubleshooting/02-*` §2.2。
- 【已验证】多用户/槽位陷阱：只换锁屏壁纸不改 system 槽时，`alive()` 仍按 system 槽判定，会出现"看起来是系统壁纸但 AOD 仍按项目壁纸" —— `troubleshooting/02-*` §2.3 B4。
- 【已验证】`org.aliveclean` 的 app uid 是 **`u0_a530`**（`scene.xml` 等私有文件的属主必须是它，否则文件的属主/权限不对）—— `history/02-*` §8.8 复原命令、`ai/02-*` §5.3。
- 【已验证】`Settings.Secure` 的写入需要 root/系统权限；UI/普通进程读不到时由模块走 shell（`su 1000`）—— `history/03-*` Secure 键表注。

## 3. MIUI / HyperOS 行为事实

### 3.1 AODView 生命周期

- 【已验证】`com.miui.aod.AODView` 构造发生在上电后的锁屏阶段（实测 attach 栈约 23:09:31），此后**整机不再重建**；因此注入机会只有一次，丢了这个实例就再没有第二次 —— `troubleshooting/02-*` §9.5。
- 【已验证】构造那一刻用户往往还没解锁，读 credential-encrypted 的 `SharedPreferences` 会抛 `IllegalStateException`；据此判成"用户关了 AOD"是错的（曾导致 `aodRoot` 被永久清空 = 稳定息屏无球）。现在用三态 `SCENE_UNKNOWN` + 2s×15 次重试处理 —— `HyperOsAod.java:86-90`；`troubleshooting/02-*` §9.5。
- 【已验证】AODView 子 View 结构（HyperOS 4.0.0.33）：`[0 不透明黑底 View][1 AodSurface(ours)][2 AodContainerView][3 NotificationAnimationView][4 ViewStub]`；注入点 = index 1（黑底之上、时钟容器之下）—— `T12` 日志，`troubleshooting/02-*` §9.5。
- 【已验证】`AodSurface` 是 `TextureView`，初始 `alpha=0`，只有首帧回调才淡到 1；看门狗 `ALPHA_WATCHDOG_MS=1500`，注入重试 `INJECT_RETRY_MS=200 × 25`，注入延迟 `ATTACH_DELAY_MS=950` —— `HyperOsAod.java:19-25`。
- 【已验证】"注入了"≠"有画面"：`injected into the AOD view` 只证明 `aodRoot != null`，必须继续看 `T04 surface#create`→`T05 texture#available`→`T13 alpha=1.0 parent=AODView` —— `troubleshooting/02-*` §1.5、§9.3 A-4。

### 3.2 2038 悬浮窗不可行

- 【已验证】`TYPE_APPLICATION_OVERLAY`(2038) 窗口在 doze 期间被 WindowManager 策略隐藏：`dumpsys window` 显示 `ty=APPLICATION_OVERLAY  mPolicyVisibility=false  isVisibleByPolicy=false  isOnScreen=false`，`Surface: shown=false mDrawState=READY_TO_SHOW`，即使内容已经画出来 —— `troubleshooting/02-*` §9.5 证据 1。
- 【已验证】结论：**在本机不要设计任何依赖 2038 兜底的 AOD 方案**，唯一可行路径是注入 AOD 自己的层级（`AodSurface`）—— 同上。`AodOverlay` 保留但只是不可靠的旧兜底 —— `facts/01-*` §7。

### 3.3 doze 期间可能没有 vsync

- 【已验证】熄屏/doze 时 Choreographer **可能整段不发 vsync**；`RenderLoop.schedule()` 里 `framePosted=true` 只有 `onVsync()` 会复位 → 回调不来就永久卡死，首帧永不出现（现象：日志有 `alpha watchdog fired, alpha=0.0`，画面不出来）—— `troubleshooting/02-*` §9.5 证据 7。
- 【已验证】兜底：`schedule()` 里 120ms `vsyncWatchdog`，到点 `framePosted` 仍为 true 就直接渲染一帧，日志 `vsync watchdog: drawing without Choreographer` —— 同上。
- 【已验证】推论（对后续开发）：AOD 下任何"靠每帧回调推进"的渲染都必须自带 vsync 兜底，不能假设 vsync 一定来 —— 同上。

### 3.4 显示状态与截图

- 【已验证】只有 `dumpsys display | grep mState=` 到 `DOZE` 时截图才有意义；`mState=DOZE_SUSPEND`（深度休眠）截出来**必然全黑**，不是模块问题（23:44–23:46 曾因此误判）—— `troubleshooting/02-*` §9.5。
- 【历史】AOD 起屏不是熄屏立即：曾出现熄屏后约 **23s** 才起屏，导致定时截图时序错位 —— `history/02-*` §8.4（一次观察，未做多次采样）。实用做法：轮询 `mState` 而不是按秒数猜；要抓稳态就等 `mState=DOZE` 后再截。
- 【已验证】验证"有球/无球"可量化：截取球区域（y=200–700，缩到 40×20）统计亮像素。失败样本 `0/800`；正常样本 86–129/800 —— `troubleshooting/02-*` §9.5。
- 【历史】`screenrecord` 录屏不一定显示 AOD 注入层；验证 AOD 内容优先用 `screencap` —— `build/01-*` §7.2；`troubleshooting/02-*` §4 旧问题 6。

### 3.5 全屏 AOD 标志是 MIUI 自己算的

- 【已验证】反编译 SystemUI 可见 `MiuiFullAodManager.onWallpaperChanged()`：
  `isWallpaperTypeSupport = isDefaultLockScreenTheme() && isMiuiWallpaperComponentUsing() && !"super_wallpaper".equals(mKeyguardWallpaperType)`；
  `updateSettings()` 用它算 `full_screen_aod_support`，只有算成 0 时才顺带写 `full_screen_aod_on=0` —— `troubleshooting/02-*` §9.2。
- 【已验证】如果我们把捕获到的 `isWallpaperTypeSupport=true` 写回去，MIUI 就永远算 `support=1` → 系统壁纸下 AOD 一直按全屏渲染（用户看到的就是"怎么设都是自定义"）。现在由 `reconcileNative()` 让 native 自己重算 —— 同上。
- 【已验证】`full_screen_aod_support=1` / `full_screen_aod_disable_reason=0` 在系统静态壁纸下是 **MIUI 算出来的正常值**（静态 MIUI 壁纸 + 默认锁屏主题 → type support = true），**不代表设备支持全屏 AOD**（设备级能力见 §2）—— `troubleshooting/02-*` §9.5 证据 4。
- 【已验证】AOD 样式下拉的两项是 MIUI 原生的：「自定义」→ `full_screen_aod_on=0`，「和锁屏样式一致」→ `1`；两种都能选中且留得住 —— `troubleshooting/02-*` §9.5 证据 5。
- 【已验证】"让设置项可点"和"让设置项生效"必须同时成立：只放开一半比锁死更糟（曾出现项目壁纸下能选「自定义」但效果不变，最终恢复 `lock(row,spinner)`）—— `troubleshooting/02-*` §12.1。
- 【已验证】反编译可见 `fullAodEnable = isDeviceSupport && mAodEnable && mAodFullScreenEnable && isFullAodSupport`：四个条件任一为 false 就没有全屏 AOD，补能力必须补到 `isFullAodSupport` 这一层 —— `troubleshooting/02-*` §9.2。
- 【已验证】`doze_always_on=0` 时任何 AOD 注入都应停止，日志 `AOD scene skipped: AOD is disabled`；壁纸不是我们的时日志 `AOD scene skipped: wallpaper is not ours`。看到这两条不是 bug，是守卫在工作 —— `build/01-*` §7.3。
- 【已验证】`AodOverlay` 走 2038 时失败日志形如 `overlay add failed … appop`（`OPSTR_SYSTEM_ALERT_WINDOW` 被拒），属预期，不要为此去改 appops —— `troubleshooting/03-*` §3.4。

### 3.6 唤醒/转场期间的分层行为

- 【已验证】唤醒时壁纸引擎会连续切构图：`mode 0(AOD) → 2(锁屏) → 1(桌面)`；诊断日志形如 `scene send mode=0->2 animate=true`、`scene reconcile … mode=2->1` —— `troubleshooting/02-*` §12.4。
- 【已验证】原生合成按 `ratio=(aod,lock,home)` 三层混合；实测一次「启航 + 锁屏带纹理」的息屏→桌面：`t=722 ratio=0.43/0.00/0.57`、`t=1046 ratio=0.11/0.00/0.89`，即 **AOD 层与桌面层交叉淡出约 1 秒**，且**锁屏层权重恒为 0** —— `troubleshooting/02-*` §12.8。
- 【已验证】"双层/残影"的观感阈值取决于两层是否相似：锁屏选了纹理而桌面没选 → 两层差别大 → 看成双层；两边都选纹理或锁屏选"无" → 几乎看不出。已用 `blendDuration=150`（仅 `aod==0 && previous==0 && next==2 && lock>=1`）把叠加压到约 150ms，`t=183 ratio=0.99 → t=333 ratio=0.03` —— 同上。
- 【已验证】锁屏层是否走玻璃程序由 `options.lock` 决定，和 Java 侧那 20 个 shape 参数无关；所以"改参数能让桌面层变干净"这条路走过三次都无效 —— `troubleshooting/02-*` §12.7。
- 【已验证】方法论事实（本项目已付代价换来）：没有可控复现时先做 A/B 整文件还原（`git checkout <基线> -- <file>`）再判断现象是否随之消失，不要对着代码猜原因（12.5 曾误判一次，12.6 用还原法推翻）—— `troubleshooting/02-*` §12.5/§12.6、`ai/02-*` §3.4。

## 4. 小米 AICR / 主体分割（com.xiaomi.aicr）

## 5. 图片解码与导入事实

> 数据全部来自 `features/06-*` §2 的同机实测（26MB / 9248×6944 JPEG），不要重新编数字。

- 【已验证】`ImageDecoder` 即使把目标压到 64px 也要 971–1158ms（本质是整幅解码后再缩），比 `BitmapFactory` 慢 3–4 倍 —— `features/06-*` §2.1。
- 【已验证】同一张图 `BitmapFactory`：全尺寸 573–964ms；`inSampleSize=4`（→2312×1736）226–241ms；`inSampleSize=8`（→1156×868）235–280ms（受 I/O 限制，再小也不更快）—— 同上。
- 【已验证】PNG(q100) 落盘 2312×1736 需 **1658–2564ms / 6.58MB**；JPEG(q95) 只需 64–189ms / 1.58MB。所以"导入慢"的大头是**编码**不是解码 —— `features/06-*` §2.2。
- 【已验证】复制 25MB 源文件只需 8–11ms：**复制原图（无损）比"缩放+重编码"又快又好**，代价只是占盘更大 —— `features/06-*` §2.3、§4。
- 【已验证】取宽高不要整套解码：`PhotoDecode.bounds()` / `VivoImages.size()` 只读文件头，省一次约 80ms 的全量解码 —— `features/06-*` §1、§3。
- 【已验证】`PhotoDecode.decode(..., maxEdge, allowBelow)` 的 `allowBelow` 只用于显示（结果可落在目标 0.7–1.4 倍），**导出必须传 false**，否则会缩水 —— `features/06-*` §3。
- 【已验证】JPEG 的 1/8 采样解码仍要扫完整个码流，所以 4 与 8 的耗时差距远小于像素数之比 —— `features/06-*` §2.1。

## 6. 构建事实

- 【已验证】必须设的四个环境变量（缺一个就失败）：`JAVA_HOME`、`ANDROID_HOME`、`ANDROID_SDK_ROOT`、`ALIVEHS_NATIVE_SO` —— `ai/02-*` §4.1；`build/01-*` §2.1。
- 【已验证】native 库环境变量名是 **`ALIVEHS_NATIVE_SO`**，不是 `HYPERALIVE_NATIVE_SO`（`docs/port/*` 里的旧命令照抄会失败）；本机没有 `cargo`，不设它会在 `cargo test` 那步 `FileNotFoundError` —— `build/01-*` §2.1；`tools/build_release.py` 的 `prebuilt = os.environ.get("ALIVEHS_NATIVE_SO")`。
- 【已验证】`--no-checks` 是**必须**的：`CHECKS` 列了 9 个脚本，而 `tools/` 下只有 `check_layout.py`、`check_xiaomi_assets.py`（2026-11-16 复核：`glob tools/check_*.py` 仅此两个）；且 `check_layout.py` 引用的类里 `AodTransitionWindow`、`ContinuousAodPolicy`、`ImmersiveBackdropPolicy` 已删除，实跑直接 javac 失败 —— `build/01-*` §3.1；`tools/build_release.py` 的 `CHECKS`。
- 【已验证】**构建成功的判据不能只看 `sha=`**：javac 失败时 `dist/SHA256SUMS` 仍是上一版的哈希。要看输出里没有 `error:` / `错误:` / `Traceback`，并与 `dist/build-report.json` 的 `sha256`、`bytes` 对照 —— `ai/02-*` §4.3。
- 【已验证】"这个 APK 是不是这份源码构建的"用 dex 串校验：在 `classes*.dex` 里搜当前源码独有的日志串（如 `vsync watchdog`、`aod mode enter skipped`、`full aod hooks=`）；有 MISSING 就先重构建 —— `build/01-*` §2.2.1。
- 【已验证】产物大小量级：当前约 **283MB**（`58e0004` = 283,541,264 B，`f2630bc` / `56a0fb5` 同）；含 ONNX 时代是 307–308MB（b1c = 308,625,742 B），删 ONNX 后 −22.7MB —— `history/01-*` §1。
- 【已验证】APK 里 assets 静态素材约占 88%（b1c：assets 压缩后约 271MB / 解压 306MB，`lib/` 约 19MB，dex 约 6.3MB），所以构建/安装/传输都慢，属正常 —— `facts/01-*` §3.1。
- 【源码事实】构建脚本 `javac` 直接 glob `app/java/**/*.java`，`sources2.txt` 不再需要维护（新增类不用改列表）—— `tools/build_release.py`；`build/01-*` §2.1。
- 【源码事实】流水线：`aapt2 compile/link → javac（含 tools/ui-api 与 xz 源码）→ D8 → zipalign → apksigner`；签名密钥默认 `local/development.jks`（alias `development`），`--skip-sign` 可跳过签名 —— `tools/build_release.py`。
- 【源码事实】脚本只认两个开关：`--no-checks`、`--skip-sign`；没有"修一半检查器"的开关，检查器修好前一律带 `--no-checks` —— `tools/build_release.py` `main()`。
- 【源码事实】产物名固定 `dist/AliveHS-<versionName>-arm64-v8a.apk`（`versionName` 从 `AndroidManifest.xml` 读），不随构建号变化，所以**同名的旧文件会被直接覆盖**，靠 SHA 区分 —— 同上。
- 【已验证】每次构建成功 + dex 校验通过后**立刻存档** `dist/save/<sha256前7位>.apk` 并重算哈希比对；否则事后无法回滚（08a0/73b54/0ecc/f2d2/5f41/b920 只剩 SHA）—— `build/01-*` §2.4、§9.4。

- 【源码事实】工作区路径含中文（`C:/Users/.../项目开发/HyperAlive`），`aapt2` / `zipalign` 这类 SDK 原生二进制在 Windows 命令行上**不接受非 ASCII 绝对路径**，脚本一律传相对路径（`rel()`）；javac 的参数文件按平台字符集解码，因此里面只能是 ASCII（`arg_path()`）—— `tools/build_release.py` 两个函数的注释。
- 【已验证】native 库是预编译件：`.tmp/build/libalive_clean.so`（467,592 B，2026-11-05），本机没有 `cargo`，所以走 `ALIVEHS_NATIVE_SO` 分支而不是 `cargo build` —— `build/01-*` §1、§2.1。

- 【已验证（规则）】构建时间一律取文件时间戳（`Get-Item` 的 `LastWriteTime`），**禁止编造时间**；曾因编造构建/装机时间被用户当场质问 —— `ai/02-*` §4.6、`troubleshooting/02-*` §12.3。
- 【已验证】写 XZ 源码前会校验 `vendor/xz/xz-1.12-sources.jar` 的 SHA-256（`c35c682f…`），Xposed API stub 必须在 `vendor/libxposed/classes.jar`，缺失即直接 `fail`（不会现场补）—— `tools/build_release.py`。
