## 1. 核查方法

| 手段 | 覆盖什么 |
|---|---|
| `git status --porcelain` / `git log --date=iso` / `git diff --shortstat` / `git ls-files` | 已跟踪/未跟踪、提交历史、未提交改动规模、被跟踪文件清单 |

| 解包 APK 的 `classes.dex` 按字节搜源码独有日志串 | 产物 ↔ 源码一致性（方法见 `05-*` §2.2.1） |

| `Get-ChildItem -Recurse` 统计 | `app/`、`.tmp/`、`dist/`、`tools/` 的实际内容与体积 |
| 实跑 `python tools/check_layout.py` | 构建检查器是否真的坏了 |

## 3. P0-1：b1c 的源码没有进 git

**事实**：

- `git log` 里最后一个代码提交是 `fc8124f`（2026-11-07 23:30），之后只有 `005ac13`（文档）。
- `git status` 显示 21 个 `app/java/org/aliveclean/*.java` 被修改，`git diff --shortstat` 为 `2086 insertions(+), 366 deletions(-)`（含我这轮改的 kb 文档；不含文档时是 `1898 insertions(+), 335 deletions(-)`）。
- 这些文件最后修改时间 ≤ 2026-11-15 16:05:15，`dist/AliveHS-0.1.0-arm64-v8a.apk` 生成于 16:05:56。
- APK 的 `classes.dex` 里能搜到只有当前工作区源码才有的字符串：`aod mode enter skipped: AOD is disabled`、`aod restore cancelled: wallpaper is still ours`、`scene re-attached after misses`、`inner AODView not up yet, waiting`、`full aod hooks=`、`AOD scene skipped: wallpaper is not ours`、`tm ni7 replaced`、`alive_aod_restore_set`（8/8 命中）。

**结论**：【已验证】b1c 是用当前未提交的工作区构建的；git 历史里**不存在**能重建 b1c 的提交。

**风险（按严重度）**：

1. 任何 `git checkout -- app/`、`git stash`、`git reset --hard`、切分支，都会让 b1c 的源码永久消失——APK 还在，但改不动、回不去、无法二分。
2. 下一任若按 `06-*` 的说法“checkout 某版本对照”，会拿到 2026-11-07 的代码，得到完全不同的行为，却以为在做回归。
3. 出问题时无法回答“这个行为是哪次改动引入的”，因为改动从来没被切成提交。

**建议处理（待用户确认，本轮未做）**：

```bash
# 方案 A（推荐）：切分成 2 个提交，保留可读历史
git add app/java tools/build_release.py && git commit -m "fix(aod): b1c baseline - steady AOD, full AOD guard, preview hooks"
git add docs/port && git commit -m "docs: import 2026-11-14 handover/port snapshots"
git tag b1c-20261115            # 给 APK 一个可引用的名字
git add tests/aodmode tests/aodpreview tests/aodprovider && git commit -m "test: add aodmode/aodpreview/aodprovider host tests"

# 方案 B（最快）：一个提交打包现状，先止血再谈可读性
git add -A ':!.jxai' && git commit -m "chore: snapshot b1c working tree (source of dist/AliveHS-0.1.0)"
```

不建议直接 `git tag` 而不提交——tag 只指向已有提交，指不到工作区。
